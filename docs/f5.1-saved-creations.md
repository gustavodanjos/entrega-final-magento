# F5.1 — Saved Creations Integration Contract

## Overview

The F5.1 backend is responsible for saving sneaker configurations associated with authenticated customers.

The implementation consists of:

- `SavedCreation` — Magento model.
- `ResourceModel/SavedCreation` — database persistence mapping.
- `SavedCreationRepository` — save and hash lookup operations.
- `SaveCreation` — business rules, validation and persistence.
- `Controller/Creation/Save` — authenticated HTTP endpoint.

The implementation uses the existing `nuvem_atelie_criacao` table.

**Current limitation:** Saving is intentionally disabled while the provisional configuration validator is active. F1.4 must provide the real validator before saving can be enabled.

## 1. Save endpoint

**Method:** `POST`

**Path:** `/atelie/creation/save`

**Example URL:** `https://final-project.test/atelie/creation/save`

This is a Magento frontend controller endpoint, not a `/rest/V1/` Web API endpoint.

### Authentication and CSRF

- The customer must be authenticated.
- The request must include the current Magento `form_key`.
- The customer ID is obtained from the server-side session, not from the request payload.
- Requests must use POST.
- The frontend must not send or trust a customer ID.

### Request format

Send the request as `application/x-www-form-urlencoded`, using these fields:

| Field | Type | Description |
|---|---|---|
| `form_key` | string | Current Magento frontend form key |
| `sku` | string | SKU of the configurable sneaker |
| `name` | string | Customer-defined creation name |
| `configuration` | string | JSON-encoded configuration |

The `configuration` field must contain a serialized JSON object following the existing configuration contract.

Example:

```json
{
  "tamanho": 38,
  "gravacao": "LUIZ",
  "selecoes": [
    {
      "grupo": "cabedal",
      "componente": "CAB-TRICO-LAVANDA"
    }
  ]
}
```

The `selecoes` field must be a JSON array, including when empty (`[]`). A JSON object (`{}`) is not a valid replacement.

The backend checks the request structure before calling the saved creation service. The final rules for allowed sizes, components and engraving depend on the real F1.4 validator.

### Frontend JavaScript example

```javascript
const formKey = document.querySelector('input[name="form_key"]')?.value;

const configuration = {
    tamanho: 38,
    gravacao: 'LUIZ',
    selecoes: [
        {
            grupo: 'cabedal',
            componente: 'CAB-TRICO-LAVANDA'
        }
    ]
};

const body = new URLSearchParams({
    form_key: formKey,
    sku: 'NUVEM-RUNNER',
    name: 'My Sneaker',
    configuration: JSON.stringify(configuration)
});

fetch('/atelie/creation/save', {
    method: 'POST',
    credentials: 'same-origin',
    headers: {
        'Content-Type': 'application/x-www-form-urlencoded; charset=UTF-8'
    },
    body: body.toString()
});
```

The example illustrates the request format. The actual Knockout implementation must use the studio's current SKU and configuration, not the example values.

## 2. Responses

### Successful save — HTTP 200

```json
{
  "success": true,
  "hash": "0123456789abcdef0123456789abcdef",
  "message": "Creation saved successfully."
}
```

The hash is the public identifier for the saved creation.

It consists of 32 hexadecimal characters generated using cryptographically secure random bytes.

The response must not expose `criacao_id` or `customer_id`.

### Customer not authenticated — HTTP 401

```json
{
  "success": false,
  "message": "Customer login is required."
}
```

The frontend is responsible for guiding the customer through login and restoring their unsaved configuration afterward.

The current backend response does not automatically redirect or preserve the configuration.

### Invalid form key — HTTP 400

```json
{
  "success": false,
  "message": "Invalid form key."
}
```

Magento's native CSRF processing can reject the request before this controller executes. In that situation, the HTTP response may differ from the controller's JSON response.

### Invalid request or configuration — HTTP 400

```json
{
  "success": false,
  "message": "Invalid configuration structure."
}
```

Other validation failures can return different messages.

### Provisional validator active — HTTP 503

```json
{
  "success": false,
  "message": "Creation saving is not available yet."
}
```

This response is intentional. The implementation must not save creations until a real configuration validator is available.

### Unexpected failures

Unexpected failures are not currently normalized into a dedicated JSON error response.

The frontend must handle network failures, non-JSON responses and unexpected server errors without assuming the save succeeded.

## 3. Persistence

The saved record contains the following information:

| Field | Origin |
|---|---|
| `criacao_id` | Database-generated internal identifier |
| `hash` | Random public identifier |
| `customer_id` | Authenticated customer session |
| `sku` | Validated request input |
| `nome` | Customer-defined name |
| `configuracao` | Serialized and normalized configuration |
| `publica` | Initially `0` |
| `curtidas` | Initially `0` |

The configuration serializer normalizes the stored configuration according to the existing F0.7 contract.

The internal numeric identifier must not be used in customer-facing URLs.

## 4. Integration dependencies

### F1.4 — Real configuration validator

F1.4 must supply the production implementation of `ConfigurationValidatorInterface`.

The saved creation service calls:

```php
$validator->validate($sku, $configuration);
```

An invalid configuration must prevent persistence.

The existing provisional validator does not provide real validation and therefore blocks saving.

### F3.2 — Knockout studio integration

F3.2 must:

1. Add the Save Creation action to the studio.
2. Obtain the current SKU and configuration.
3. Ask the customer to name the creation.
4. Submit the required fields and Magento form key.
5. Display save success and validation errors.
6. Handle unauthenticated customers without losing their configuration.
7. Use the returned hash when the shareable creation URL becomes available.

The frontend must prevent accidental duplicate submissions while a request is pending.

### F5.3 — Open or remix a saved creation

F5.3 must provide the URL and loading flow for a saved creation identified by its public hash.

It must load the saved SKU and normalized configuration and restore the corresponding sneaker in the studio.

F5.1 currently returns the hash but does not provide a functioning shareable URL.

The handling of private versus public creations must be agreed upon before exposing saved configurations to unauthenticated users. The `publica` database field defaults to `0`.

These checks do not constitute final end-to-end acceptance. Full validation requires F1.4, F3.2 and F5.3 integration.
